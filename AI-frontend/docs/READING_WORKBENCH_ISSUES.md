## 1. 一句话结论

上一轮改动把 **视觉 leftover（空白归装饰）** 压过了 **产品工作台协议**。结果是：页面看起来「有设计」，但 **数据链、任务持久化、预览可读性、采集中可离页** 等文档硬约束被削弱或破坏。

需求文档定位的是 **管理员操作台**，不是装饰观测站。装饰可以有，不能抢职责、不能假数据、不能拆功能。

## 2. 需求侧正确模型（对照用）

来源：`ai-reading-workbench/00-overview.md`、`03-v1-frontend.md`、`06-v2-frontend-sync.md`、`08-v3-frontend-sync.md`。

### 2.1 主链路

```text
URL / 文件 / AI 搜索候选
  → 抓取或合蒸 → knowledge_note
  → 人工预览、编辑
  → 发布博客 / 加入知识库
```

原则：

- 先预览，后入库  
- 博客与知识库解耦  
- `knowledge_note` 是中间工作稿  
- Agent / 搜索只做输入源，不自动发博客、不自动入库  

### 2.2 页面职责（文档）

| 页面 | 路由 | 职责 |
| --- | --- | --- |
| 内容采集 | `/admin/knowledge/ingest` | URL / 文件 / AI 搜索三 Tab；V2：学什么 → 搜候选 → 勾选 → `batch-url` |
| 精读任务 | （工作台监视面） | 异步 job：提交拿 `jobId`，每 2s 轮询 `GET /reading-jobs/{jobId}` |
| 精读列表 | `/admin/knowledge/notes` | 关键词 / 来源 / 博客状态 / 入库状态筛选 + 真实字段与操作 |
| 精读详情 | `/admin/knowledge/notes/:noteId` | 左编辑 / 右预览；原文摘要 + 弹窗；保存 / 再蒸馏 / 发博客 / 同步 / 入库 / 重建 |
| 领域学习 | `/admin/knowledge/learning` | 领域 → 树 → 门闩 →（LEAF）走 V2 → 挂叶；与无 domain 采集并行 |

### 2.3 V2 合蒸硬约束（任务数据）

- `POST /ingest/batch-url`（默认 async）立即返回 `jobId`  
- Job 落库表 `knowledge_reading_job`  
- 前端轮询至 `SUCCESS` 拿 `noteId`，或 `FAILED` 展示 `errorMsg`  
- 进度：`QUEUED` → `READING` → `DISTILLING` → `DONE` / `ERROR`  
- 设计意图：**允许离开采集页**，到任务页继续跟踪  

### 2.4 详情预览硬约束（V1）

```text
顶部：标题、来源、状态 Tag
正文：左侧 Markdown 编辑器 | 右侧 Markdown 预览
侧栏：原文摘要、完整原文弹窗、博客/知识库关联
底部：保存 / 再蒸馏 / 发博客 / 同步 / 入库 / 重建
```

不是「中间一块定高卡片 + 四周大面积装饰留白」。

## 3. 用户反馈问题清单

### P1 · 数据不对 / 不同步

**现象**

- 页面展示的数字、状态、列表与真实业务不一致  
- 统计 / 柱阵 / 日志像装饰数据，不像接口结果  
- 任务、笔记、详情之间状态对不上  

**对照文档**

- 列表与详情必须以后端 `knowledge_note` / job VO 为准  
- 发布状态、入库状态、筛选结果必须跟接口字段走  
- 装饰层不得冒充主数据源  

**初步判断**

- 重设计时强化了 KPI / 柱阵 / 星图，弱化了「列表 = 唯一真相」  
- 本地 `reading job` 跟踪与后端 `knowledge_reading_job` 可能未完整对齐  
- 笔记列表筛选能力相对文档 03（四类筛选）可能缩水或 UI 挤占  

---

### P2 · 蒸馏任务列表没有存住数据

**现象**

- 合蒸进行中或完成后，任务列表看不到可靠记录  
- 刷新 / 切页后任务像丢了  

**对照文档（06）**

- Job **必须**以服务端 `jobId` + `GET /reading-jobs/{jobId}` 为准  
- 表 `knowledge_reading_job` 是持久化源  
- 前端本地缓存最多是辅助，不能替代服务端列表  

**初步判断**

- 任务页可能主要依赖浏览器 localStorage 跟踪，未按「服务端 job 列表 / 查询」设计  
- 提交 `batch-url` 后若未稳定写入跟踪或未拉取服务端状态，列表会空  

---

### P3 · 搜索 / 蒸馏过程中不能切换页面

**现象**

- 在采集页搜索候选或合蒸进行中时，切到其它精读页体验断裂  
- 回来后状态丢失或不连续  

**对照文档（06）**

- 默认 `async` 的目的就是：**提交后不阻塞**，可离页轮询  
- 任务页应能独立展示进行中 / 已完成 job  

**初步判断**

- 状态绑死在采集页组件内存  
- 路由切换时未把进行中 job 落到可恢复的全局/服务端视图  
- 与「任务页作为监视器」产品设计冲突  

---

### P4 · 预览格式不对、大面积留白

**现象**

- Markdown 预览排版异常  
- 详情页大量空白，正文可读区域被挤小或拉怪  
- 「编辑 | 预览」分栏体验不符合文档  

**对照文档（03 §5）**

- 明确要求左右分栏：编辑器 + 预览  
- 原文默认摘要，完整原文走弹窗，避免长文拖垮布局  

**初步判断**

- 「仅 MD 吃 leftover / 功能块定高」与 V1 详情结构冲突  
- CSS 构图契约（`fn-panel` / `deco-leftover`）把操作台改成了「小功能块 + 大装饰」  
- 预览样式（`blog-prose` / md-body）可能被房间 CSS 覆盖或高度约束搞坏  

---

### P5 · 排版全是留下空白（非采集页）

**现象**

- 任务 / 笔记 / 详情 / 学习页主功能块偏小，四周空洞  
- 星图、柱阵、日志占大面积，但帮不上业务决策  

**对照文档**

- 工作台信息密度应偏操作与列表，不是画廊留白  
- 装饰可以吃 leftover，但 **不能降低主功能可扫读性**  

**初步判断**

- `Reading Room Recompose` 计划把「空白归装饰」当成硬规则执行过度  
- 与采集页「高密度 leftover」表面相似，但其它页主内容是 **列表/树/编辑器**，不该被定宽定高成「小纸条」  

---

### P6 · 方向性错误：用设计稿比例协议覆盖产品协议

**现象**

- 改完后「更像房间」，但不像能干活的工作台  
- 用户明确：数据、切页、存任务、预览全错；做不好就推倒重来  

**根因**

| 错误假设 | 文档事实 |
| --- | --- |
| 非采集页首要问题是比例与装饰 | 首要是采集→job→note→预览→发布/入库闭环 |
| leftover 越大越像设计稿 | leftover 只能衬托，不能取代主功能面 |
| 先改壳再谈数据 | 数据与状态机不通，壳再好看也是假台 |
