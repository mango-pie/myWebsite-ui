## 1. 一句话总评

现有设计**成熟度高、自省意识强**:先预览后入库、博客与知识库解耦、async 可离页、V3 门闩分类、P1~P6 自我纠偏,方向全部正确。

但整体仍是**「单向管道」**——发现→蒸馏→确认→沉淀→挂树,终点是"存下"而非"学到"。最值得做的结构性改动,是把这条链路升级为**学习闭环**;其余建议都是在其上的打磨。

设计上的强项(保留):

| 点 | 为什么好 |
| --- | --- |
| 先预览,后入库 | 人工确认是唯一真相闸门,避免垃圾入库 |
| 博客/知识库解耦 + `knowledge_note` 为工作稿 | 单一编辑真相源,展示与检索互不污染 |
| async 异步 job + 可离页轮询 | 有明确设计意图,不是炫技 |
| V3 门闩(related/intent) | 用 AI 判定引导而非放任,方向对 |
| leftover/compose contract 自省 | 承认"装饰抢职责"是坑,并给出纠正 |

## 2. 结构性建议:从「单向链路」到「学习闭环」

### 2.1 现状

```text
发现(URL/文件/搜索)
  → 合蒸/精炼
  → 人工确认
  → 分流博客/知识库
  → (V3)挂树 → 按枝浏览
```

管线止步于"沉淀",缺少**从沉淀回到学习**的反馈。

### 2.2 目标

```text
发现 → 蒸馏 → 确认 → 沉淀 → 挂树
                              ↓
                   复习/自测(暴露薄弱)
                              ↓
                    空枝/薄弱提示补学
                              ↓
                         再采集
```

### 2.3 三个落地项

1. **复习模式(利用已有蒸馏结构)**
   - 默认蒸馏结构(核心思想 / 关键知识点 / 代码精髓 / 延伸问题)天然适合生成**自测题**
   - 建议:note 内嵌"复习模式",按 key points 提问、答案折叠;V3 按枝复习时逐枝抽题
   - 这比"按枝浏览"更接近"真的在复述"

2. **轻量复习状态机**
   - note 状态:`新学 / 复习中 / 已掌握`
   - V3 树上可聚合为"此枝掌握度",空枝提示补学升级为"薄弱枝提示巩固"
   - 状态变更仅本地语义,不碰博客/入库状态机,避免状态爆炸

3. **闭环价值**
   - 从"采集工具"升格为"学习系统"
   - 复习中发现薄弱 → 空枝补学 CTA 有真实触发时机,而不是静态按钮

## 3. 高优先级:三个真实风险

### 3.1 门闩依赖单次 LLM 判定,稳定性没被正视

**风险**:`related`(布尔)+ `intent`(三选一)由单次判定决定整条路径的启用/禁用,LLM 结果存在噪声。

**建议**:

| 项 | 做法 |
| --- | --- |
| 置信度 | 返回 `confidence`,低置信时 UI 走"可能相关"双选项,而非硬编码禁用 |
| 缓存 | 按 `domainId + question` 缓存判定结果,避免同一问题重复烧模型 |
| 跳过策略 | "不提供跳过门闩"对新手好,对老用户是负担 → 改为"带理由跳过",后端只对 `intent=LEAF` 的合蒸做强校验,BRANCH/CHAT 允许人工 override |
| 补救对称 | 现有补救(重判定/树编辑器)保留,补"用户标记判定错误"入口回写,形成数据闭环 |

### 3.2 合蒸溯源停留在文档级,未到句级

**风险**:`raw_text` 保留了原文,但精读正文与来源之间没有锚点,无法回答"这句话是哪来的",溯源原则打折扣。

**建议**:

- 材料包物化时**按来源分块**,蒸馏输出带 `[src1] [src2]` 句级标注
- 增加**冲突检测**:多来源说法矛盾时,精读应**暴露分歧**(并列两种说法),而不是静默平均
- 效果:回读时可一键跳到原文对应块,溯源从"能查"升级为"能跳"

### 3.3 任务"可离页"但"回不来"

**风险**:async 承诺不阻塞、可离页,但没有"完成时如何召回用户"的设计;单 RUNNING 槽 + 排队任务,用户切走即遗忘。

**建议**:

- 任务完成时**浏览器通知 / 声音提示**(admin 专用,可关)
- 把"可以离开"变成"离开后会被叫回来"
- 明确超时与召回契约:QUEUED 超过 N 分钟、FAILED 时如何提醒

## 4. 中优先级:补两个缺口

### 4.1 去重缺失

**问题**:同一 URL 重复采集、搜索结果与已有 note 高度相似,目前全靠人眼。

**建议**:

- URL hash 去重
- 标题 / 正文相似度(embedding 或 minhash)
- 采集与搜索候选上直接标注"已在库 / 已读"
- 比事后 dedup 省事,且在合蒸勾选阶段就能避免重复材料

### 4.2 失败 / 恢复路径未进验收

**问题**:验收脚本 A~F 全部走 happy path。

**建议补充**:

| 脚本 | 场景 |
| --- | --- |
| G | job FAILED → 重试,且**保留已勾选 URL** |
| H | 合蒸部分来源失败(partial success)的展示与重读 |
| I | 同一 note 多 tab 编辑的冲突处理(以最后保存为准 + 提示) |
| J | 门闩低置信 / 判定错误的降级路径 |

## 5. 工程与安全建议

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 抓取安全 | URL 抓取加**协议白名单 + 私有网段/IP 校验 + 重定向限制** | Jina Reader 抓任意 URL,admin 专用也要防 SSRF |
| 固定舞台 | **1920×1080 固定 stage 仅用于采集页**等仪式感页;列表/详情/树用弹性流式布局,shell 固定、内容内部滚动 | 操作台面向真实浏览器窗口,P5 根因一半在此 |
| 装饰即状态 | 补充 UI 原则:**装饰必须绑定真实数据源**(遥测柱阵=真实 job 进度、星图=真实来源图谱) | P1 的正解不是"少放装饰",而是"装饰即状态" |
| 模型参数 | `distill` 用低 temperature(如 0.2~0.4)保事实性,`reading` 可近 0 | 蒸馏输出会被反复复习,幻觉成本高 |

## 6. 成本控制

### 6.1 成本构成

```text
成本 ≈ 调用次数 × 每次 token 量 × 模型单价
```

按体量排序的大头:

1. **reading 阶段**:每 URL 全文进 LLM,每单 2~5 篇 —— 次数最多、单次 token 最重
2. **distill 阶段**:pro 模型吃"整包材料"(所有页面拼接)—— 单价最贵
3. **返工**:redistill 全量重跑、reindex 全删全建 —— 纯浪费
4. **门闩 / 批量建议等小调用** —— 占比低,不值得优先优化

### 6.2 七个降本杠杆(按性价比排序)

**1. 压缩材料包(最大杠杆,两端同时省钱)**
reading 模型不要"转述全文",只输出**要点抽取 + 关键引文 + 结构化字段**(title / 结论 / 分歧点),输出 token 压到输入的 20~30%。材料包小了 → distill 的 pro 输入直接变小 → reading 输出省一次,pro 输入再省一次。

**2. 缓存 + 去重前置(最省的就是不跑)**
- URL 读页结果按 URL hash 缓存(如 30 天),同 URL 再采直接复用材料包
- 去重前置(见 4.1):"已在库 / 已读"标注,根本不进管线
- 门闩判定、搜索候选按 key 缓存

**3. 模型分层再收紧**
- 默认 **flash 全流程**;只有用户点了"发布博客 / 入库 RAG"时,才用 pro 精修一版(那是唯一需要质量的地方)
- 再蒸馏默认 flash,pro 是可选升级项,不是默认
- pro 失败 / 超时降级 flash,保证链路不空转

**4. 差量返工**
- redistill:只重蒸馏**用户编辑过的段落 + 对应原文**,不整篇重跑
- reindex:只重 embedding 变化的 chunk,不删全表重建

**5. 失败预算与差量重试**
- 重试次数上限 1 次;失败来源写进 `failedSources` 后**只重读失败源**,不整单重跑
- 部分失败直接出 partial 结果,不整单作废(已花的 token 不浪费)

**6. 页内裁剪 + token 预算上限**
- Jina Reader 仅正文模式;超长文(文档 / PDF)只取首尾 + 目录,或先 flash 抽章节再按章采读
- 每 URL 读页设 token 预算上限,超长页截断而不是硬吃

**7. 用量看板**
- 每 job 落库 token 用量与估算成本,月度视图;很快就能发现"哪类来源在烧钱"(如超长 PDF),针对性裁剪
- 数据引导行为,比拍脑袋省钱可靠

### 6.3 结构性防返工:大纲确认步

勾选 2~5 篇后,先 flash 出一版**合蒸大纲**,用户点"可以,开始蒸馏"才跑 pro 全量。成本只多一次 flash(可忽略),但避免了"pro 蒸完不满意 → 再蒸馏"的双倍 pro 成本。

### 6.4 成本底线

distill 质量是这产品存在的理由。省钱优先级:先做**缓存 / 裁剪 / 差量**(零质量损失)→ 再**模型分层**(轻微可控损失)→ 最后才动蒸馏质量。前两类能砍掉 50%+ 成本,第三类基本不用碰。

## 7. 其他待解决问题

### 7.1 内容与合规

| 项 | 问题 | 建议 |
| --- | --- | --- |
| 版权边界 | 精读稿是"二次创作",再发布到博客涉及他人网站内容,目前无约束 | 发博客时**强制附原文链接**、避免大段原文照搬;可选"AI 生成声明";精读稿定位为摘要 + 转述 + 个人理解 |
| 原文失效 | 网页会改版 / 404,缓存的材料包会过期 | 材料包缓存带**失效时间 + 手动刷新**;原文失效时溯源跳转降级为"缓存快照" |

### 7.2 数据韧性

| 项 | 问题 | 建议 |
| --- | --- | --- |
| 导出备份 | `knowledge_note` 是唯一真相源,存在数据库里,有丢失风险 | 提供**整库 Markdown 批量导出**(精读稿本质是 Markdown,可迁移、可备份) |
| 供应商余额 | DeepSeek / DashScope 分开管理,余额不足时任务静默失败 | 余额不足**预警 + 自动熔断**(转低配模型或停新任务),不浪费任务 |
| 审计日志 | 发布 / 入库 / 改树是关键操作,无留痕 | 关键操作写审计日志(单用户可选,多人协作必选);**明确"单管理员"假设**,若多人需补权限与编辑锁 |
| 多 tab 冲突 | 同 note 多窗口编辑互相覆盖 | 见验收脚本 I:最后保存为准 + 提示 |

### 7.3 流程韧性

| 项 | 问题 | 建议 |
| --- | --- | --- |
| 长上下文超限 | 大材料包(多篇长文拼接)可能超 pro 上下文窗口 | 提前定义**分块蒸馏 + 拼接对齐**策略,而不是硬塞或粗暴截断 |
| 断线恢复 | 刷新 / 断网后前端轮询丢失,用户不知道任务还在跑 | 重连时**重新挂接进行中 job**(服务端是真相源,前端补恢复逻辑) |
| 多 job 风暴 | 网络抖动导致多个 job 同时失败、同时重试 | 重试加抖动退避;单 RUNNING 槽外的排队上限与优先级 |

### 7.4 体验细节

| 项 | 问题 | 建议 |
| --- | --- | --- |
| 候选质量预判 | 搜索候选只有 URL,用户难以判断值不值得读 | 候选卡片带 **flash 一句话摘要 + 域名**;成本极低,大幅提升勾选决策质量 |
| 对齐度自检 | 合蒸结果可能偏离学习目标(材料相关度参差) | distill 完成后 **flash 自检"与 goal 对齐度"**,低分提示换材料 / 重蒸 |
| note 归档 | 列表无限增长,没有清理路径 | 加**归档 / 隐藏**状态(不删除来源与树关联) |
| 标签管理 | V1 有可选标签,但无管理能力 | 标签合并 / 重命名 / 自动建议(flash) |
| 枝级综述 | BRANCH 场景下多篇 note 无聚合视图 | 一个枝攒了多篇后支持"合并生成整枝知识地图 / 综述",从已学内容生长 |
| 编辑键盘流 | 审阅页只有导航快捷键,没有编辑快捷键 | Tab(左编右预切换)、Ctrl+S(保存) |
| 大纲语义 | "学习大纲"用途未定义 | 明确 = 勾选后合蒸的**章节骨架**(合蒸时对齐大纲输出),让"半自动"成为"有结构的蒸馏" |
| 冲突状态 | 同步失败 / 需同步可能被误认为阻塞 | 明确**永不阻塞编辑**(note 是真相源),sync 仅可重试 |

## 8. 优先级排序总表

| 优先级 | 建议 | 收益 | 成本 |
| --- | --- | --- | --- |
| P0 | 复习模式 + 复习状态机(学习闭环) | 产品升格为"学习系统" | 中(纯前端语义 + 复习 UI) |
| P0 | 句级溯源 + 冲突检测(合蒸) | 溯源原则真正落地 | 中(材料包分块 + distill prompt) |
| P0 | 门闩置信度 + 可覆盖 + 缓存 | 关键路径稳定 | 小(API 加字段 + UI 分支) |
| P0 | 压缩材料包(reading 输出要点 + 引文) | **成本最大杠杆,两端省钱** | 小(prompt 改造) |
| P0 | 模型分层(flash 默认,pro 仅在发布/入库时) | 成本显著下降,质量可控 | 小(配置 + 流程) |
| P1 | 抓取安全(SSRF 防护) | 消除安全隐患 | 小 |
| P1 | 任务完成通知 | async 承诺闭环 | 小 |
| P1 | 去重(URL hash + 相似度) | 防重复学习 + 省钱 | 中 |
| P1 | 失败/恢复验收脚本 G~J | 交付质量 | 小 |
| P1 | 差量返工(redistill / reindex) | 返工成本减半 | 中 |
| P1 | 失败预算 + 差量重试 | 失败成本受控 | 小 |
| P1 | 版权合规(原文链接 + 引用边界) | 规避内容风险 | 小 |
| P1 | 导出备份(整库 Markdown) | 数据不丢 | 小 |
| P1 | 长上下文分块策略 | 大材料包可用 | 中 |
| P2 | 操作台弹性流式布局 | 真实环境可用性 | 中(布局重构) |
| P2 | 装饰即状态原则 | 解决 P1 方向 | 小 |
| P2 | 用量看板(token / 成本月度报表) | 成本可视化治理 | 中 |
| P2 | 候选摘要 + 对齐度自检 | 蒸馏质量感知 | 小 |
| P2 | 余额预警熔断 / 审计日志 / 断线恢复 | 运营韧性 | 中 |
| P2 | note 归档 / 标签管理 / 枝级综述 / 键盘流 | 体验深化 | 中 |
